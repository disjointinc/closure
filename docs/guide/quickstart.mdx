Closure is a system for metering, entitlements, and billing. Closure lets you build powerful functionality on top of these primitives, like:

1. Actioning and alerting on customer lifecycle events
1. Granting discounts and referral bonuses
1. Experimenting with plans and pricing
1. Processing buy-now-pay-later
1. Modeling marginal revenue and expenses

and more! First, though, this quickstart guide will help you set up the basics.

## Create your first plan

We recommend creating the plan and its prerequisites in the UI, but in case you want to do it all in the API, we've added sample calls below.

### Prerequisites

First, let's create the product line for the plan. Most SaaS businesses just have 1 product line, on which they have multiple plans (starter, pro, enterprise, etc).

```bash
curl -X POST http://localhost:3216/v0/product-line \
  -H 'content-type: application/json' \
  -d '{
    "name": "Default product line",
    "description": "The product line where all our plans live",
    "forceBillingCycleSynchronizationWithProductLineIds": []
  }'
```

Next, let's create a feature on that product line.

```bash
curl -X POST http://localhost:3216/v0/feature \
  -H 'content-type: application/json' \
  -d '{
    "productLineId": "<product line ID from above>",
    "name": "Slack alerts",
    "description": "Send the tenant alerts in Slack",
    "options": null,
    "applicableTaxTypeIds": null,
  }'
```

Features can be boolean values (like above), or select values. Let's create a second, select-type feature.

```bash
curl -X POST http://localhost:3216/v0/feature \
  -H 'content-type: application/json' \
  -d '{
    "productLineId": "<product line ID from above>",
    "name": "CRM",
    "description": "CRMs that can be connected",
    "options": [
      {
        "name": "hubspot",
        "description": null
      },
      {
        "name": "salesforce",
        "description": null
      },
      {
        "name": "attio",
        "description": null
      },
      {
        "name": "dynamics365",
        "description": null
      }
    ],
    "applicableTaxTypeIds": null,
  }'
```

Next, let's create a meter. Unlike features, meters can be used in more than 1 product line, since separate product lines may be pulling from the same balance (for example, an AI token balance).

```bash
curl -X POST http://localhost:3216/v0/meter \
  -H 'content-type: application/json' \
  -d '{
    "productLineIds": ["<product line ID from above>"],
    "name": "Seats",
    "description": "The number of users on a tenant",
    "applicableTaxTypeIds": null,
  }'
```

There are many important things to define for this meter: its default balance, the maximum number of credits a tenant can spend, whether and when the meter resets, the marginal cost of top-up credits, etc. However, these values all vary plan-by-plan, so we set them when creating the plan, not when creating the meter.

Finally, let's create a billing cycle. Some SaaS businesses wait until the end of a billing cycle to tally up costs (billing in arrears), while some bill you upfront before you're granted access.

```bash
curl -X POST http://localhost:3216/v0/cycle \
  -H 'content-type: application/json' \
  -d '{
    "charged": "upfront",
    "cycleLength": { "days": null, "months": 1 },
    "defaultDiscountPercentage": null,
    "name": "Monthly",
    "description": "Monthly billing cycle"
  }'
```

Most SaaS businesses offer annual plans on a discount. Let's create an annual cycle, billed net 30, with a 5-day grace period.

```bash
curl -X POST http://localhost:3216/v0/cycle \
  -H 'content-type: application/json' \
  -d '{
    "charged": "arrears",
    "cycleLength": { "days": null, "months": 12 },
    "creditPeriod": { "days": 30, "months": null },
    "gracePeriod": { "days": 5, "months": null },
    "defaultDiscountPercentage": 20,
    "name": "Annual",
    "description": "Annual billing cycle"
  }'
```

### Building the plan

A plan is the core model of "how do people pay us, and what do they get in return."

1. Most B2C or SME-focused B2B companies stick to plan defaults when assigning tenants.
1. Most enterprise-focused B2B companies treat each tenant as unique, and override many plan defaults when assigning tenants.

Wherever your business falls on that spectrum, Closure requires you to start with a plan when assigning a tenant. At its most basic, a plan is just a set of entitlements to features and meters, and a price the tenant pays.

```bash
curl -X POST http://localhost:3216/v0/plan \
  -H 'content-type: application/json' \
  -d '{
    "productLineId": "<product line ID from above>",
    "derivedFromPlanId": null,
    "name": "Starter",
    "description": "The starter plan",
    "prices": [
      {
        "cycleId": "<first cycle ID from above>",
        "amounts": [
          { "currency": "USD", "unit": "cents", "value": 2900 },
          { "currency": "EUR", "unit": "cents", "value": 2500 },
        ]
      },
      {
        "cycleId": "<second cycle ID from above>",
        "amounts": [
          { "currency": "USD", "unit": "cents", "value": 290000 },
          { "currency": "EUR", "unit": "cents", "value": 250000 },
        ]
      }
    ],
    "features": [
      {
        "featureId": "<first feature ID from above>",
        "setTo": false
      },
      {
        "featureId": "<second feature ID from above>",
        "setTo": ["hubspot", "attio"]
      }
    ],
    "meters": [
      {
        "meterId": "<meter ID from above>",
        "defaultCredits": 10,
        "limitCredits": 30,
        "reset": "billing_cycle_end",
        "rollovers": 1,
        "topUpPricesPerCredit": [
          {
            "startingAt": 0,
            "prices": [
              {
                "cycleId": "<first cycle ID from above>",
                "amounts": [
                  { "currency": "USD", "unit": "cents", "value": 500 },
                  { "currency": "EUR", "unit": "cents", "value": 430 },
                ]
              },
              {
                "cycleId": "<second cycle ID from above>",
                "amounts": [
                  { "currency": "USD", "unit": "cents", "value": 400 },
                  { "currency": "EUR", "unit": "cents", "value": 340 },
                ]
              }
            ],
          },
          {
            "startingAt": 10,
            "prices": [
              {
                "cycleId": "<first cycle ID from above>",
                "amounts": [
                  { "currency": "USD", "unit": "cents", "value": 400 },
                  { "currency": "EUR", "unit": "cents", "value": 340 },
                ]
              },
              {
                "cycleId": "<second cycle ID from above>",
                "amounts": [
                  { "currency": "USD", "unit": "cents", "value": 350 },
                  { "currency": "EUR", "unit": "cents", "value": 300 },
                ]
              }
            ]
          }
        ],
        "topUpCreditPackSizes": {
          "static": [1, 5, 10, 20]
        }
      }
    ],
    "addOnTypeIds": null
  }'
```

Plans can also have add-ons, which are mini feature sets the tenant can purchase without having to upgrade their whole plan. An example could be a "project management add-on", which might let a tenant access some project management tools in-product, and connect their Asana, Monday.com, etc. We won't create any add-ons for now.

## Assign a tenant

A plan is like a template. Assignment is when we actually apply that template to a tenant. This is also when we tweak that template; maybe a particular tenant needs slightly different features, meters, or prices than the default plan values.

> If you've been setting up the plan and prerequisites in the UI, we'd recommend **using the provided API calls** for the rest of the quickstart. The following calls are things you're likely going to do in your codebase, rather than in the Closure UI.

### Create the tenant

First, let's create the tenant within Closure. Closure's philosophy on tenants is simple: we store as little info as possible. The right sources of truth live in other systems.

1. Your tenant's email address lives in your database.
1. Your tenant's credit card number lives in your Stripe account.
1. Your tenant's profile picture lives in your file storage system, etc.

So, when creating a tenant, all you define are its IDs in those external systems.

```bash
curl -X POST http://localhost:3216/v0/tenant \
  -H 'content-type: application/json' \
  -d '{
    "externalIds": {
      "userId": "<user ID in your database>",
      "stripeCustomerId": "<customer ID in Stripe>",
    }
  }'
```

### Assign them

Let's assign the tenant to a plan.

```bash
curl -X POST http://localhost:3216/v0/tenant/<tenant ID from above>/assignment \
  -H 'content-type: application/json' \
  -d '{
    "planId": "<plan ID from above>",
    "experimentId": null,
    "cycleId": "<first cycle ID from above>",
    "startsAt": <start time, in epoch milliseconds>,
    "endsAt": null,
    "addOns": []
  }'
```

### Overrides

Let's override a feature assignment. Our plan only allows Hubspot and Attio, but let's grant Salesforce access to this tenant anyway.

```bash
curl -X POST http://localhost:3216/v0/tenant/<tenant ID from above>/feature-override \
  -H 'content-type: application/json' \
  -d '{
    "featureId": "<second feature ID from above>",
    "setTo": ["hubspot", "attio", "salesforce"]
  }'
```

Let's override a meter's assignment too. Let's bump this tenant's default seat credits to 15, and set their top up price per credit to a lower flat rate.

```bash
curl -X POST http://localhost:3216/v0/tenant/<tenant ID from above>/meter-override \
  -H 'content-type: application/json' \
  -d '{
    "meterId": "<meter ID from above>",
    "defaultCredits": 15,
    "limitCredits": 30,
    "reset": "billing_cycle_end",
    "rollovers": 1,
    "topUpPricesPerCredit": [
      {
        "startingAt": 0,
        "prices": [
          {
            "cycleId": "<first cycle ID from above>",
            "amounts": [
              { "currency": "USD", "unit": "cents", "value": 400 },
              { "currency": "EUR", "unit": "cents", "value": 340 },
            ]
          },
          {
            "cycleId": "<second cycle ID from above>",
            "amounts": [
              { "currency": "USD", "unit": "cents", "value": 350 },
              { "currency": "EUR", "unit": "cents", "value": 300 },
            ]
          }
        ]
      }
    ],
    "topUpCreditPackSizes": {
      "static": [1, 5, 10, 20]
    }
  }'
```

## Get stuff done

Now, let's use Closure to get things done in our codebase!

### Check entitlements

First, let's check what features a tenant is entitled to. With this info, we can change what's shown in our UI, what our backend allows, etc. For example, we may only want to show allowed CRMs in our "Connect CRM" tab.

```bash
curl http://localhost:3216/v0/tenant/<tenant ID from above>/feature-entitlements
```

Next, let's check what meters a tenant is entitled to. For example, we might use this to show a progress bar (i.e. 10 default seats) or tell the user how much they can buy (i.e. 20 additional seats allowed).

```bash
curl http://localhost:3216/v0/tenant/<tenant ID from above>/meter-entitlements
```

### Meter

First, let's check the tenant's balance on a meter. We might use this to show how much of a progress bar has been used up (i.e. 4 of 10 seats used).

```bash
curl http://localhost:3216/v0/tenant/<tenant ID from above>/meter-balance/<meter ID from above>
```

Finally, let's send a meter event. For example, if the tenant just added a user, we're going to want to send that info to the seats meter. We'll charge the user 1 seats credit.

> If you want to refund credits, just pass a negative value for `amountCredits`. Closure supports fractional credit amounts, up to a millionth of a credit.

```bash
curl -X POST http://localhost:3216/v0/tenant/<tenant ID from above>/meter-event \
  -H 'content-type: application/json' \
  -d '{
    "externalId": "<your idempotency key>",
    "meterId": "<meter ID from above>",
    "amountCredits": 1
  }'
```

> If you're worried about sending duplicate meter events, you can pass an `externalId` associating the meter event with some unique key in another system. Closure will deduplicate events with the same `externalId`.

After processing, we'll get back:

1. A `succeeded` status if the meter event ran successfully.
1. An `insufficient_balance` status if the meter event was rejected because the tenant had insufficient credits.
1. An `unexpected_error` status if something went wrong internal to Closure.

Metering in Closure is built to run on the hot path.

1. That means you can trust Closure meter events and meter balances to be blocking API calls.
1. It also means you don't have to think about batching meter events, eventual balance correctness, etc. Just send events when you need to, and check balances when you need to; Closure should only return accurate values, and should return them fast.
